Chapitre 1 — Introduction et Culture DevOps

1.1 Historique et Contexte

Le terme DevOps est une contraction de Development (développement) et Operations (exploitation). Il désigne un ensemble de pratiques, de méthodes et d'outils visant à améliorer la collaboration entre les équipes de développement logiciel et les équipes d'exploitation informatique.

Avant DevOps, les organisations travaillaient en silos : les développeurs écrivaient du code et le transmettaient aux équipes opérationnelles qui se chargeaient de le déployer et de le maintenir en production. Cette approche générait de nombreux problèmes : conflits de responsabilité, délais de mise en production longs, instabilité des systèmes.

1.2 Définition et Philosophie

Définition : DevOps est une approche culturelle, organisationnelle et technique qui vise à unifier le développement logiciel (Dev) et l'administration des systèmes informatiques (Ops) afin de livrer des applications de manière continue, fiable et rapide.

1.2.1 Les trois piliers du DevOps

  1. Culture : collaboration, partage de responsabilités, apprentissage continu.
  2. Automatisation : réduction des tâches manuelles répétitives.
  3. Mesure : collecte de métriques, amélioration continue basée sur les données.

1.3 Le Cycle de Vie DevOps (CALMS)

Le modèle CALMS résume les valeurs fondamentales du DevOps :

Lettre Signification
C Culture (collaboration entre Dev et Ops)
A Automatisation (des processus répétitifs)
L Lean (réduction du gaspillage)
M Measurement (métriques et feedback)
S Sharing (partage des connaissances)

1.4 Le Pipeline DevOps

Le cycle de vie DevOps comprend les phases suivantes :

  1. Plan : définition des besoins et des objectifs.
  2. Code : développement du logiciel.
  3. Build : compilation et assemblage du code.
  4. Test : vérification automatique de la qualité.
  5. Release : préparation du livrable.
  6. Deploy : déploiement en production.
  7. Operate : gestion de l'infrastructure en production.
  8. Monitor : surveillance et collecte de métriques.

1.5 Avantages du DevOps

  • Réduction du délai de mise sur le marché (time-to-market).
  • Amélioration de la qualité logicielle.
  • Meilleure stabilité des systèmes en production.
  • Réduction des coûts opérationnels.
  • Augmentation de la satisfaction client.

Chapitre 2 — Gestion de Versions et Collaboration avec Git

2.1 Introduction à Git

Git est un système de gestion de versions distribué créé par Linus Torvalds en 2005. Il permet de suivre les modifications du code source, de collaborer efficacement et de gérer plusieurs versions d'un projet simultanément.

Dépôt (Repository) : répertoire versionné contenant l'ensemble du code source et l'historique complet des modifications.

Listing 2.1 – Installation de Git

# CentOS / RHEL
sudo yum install -y git

# macOS (avec Homebrew)
brew install git

# Définir le nom d'utilisateur

# Définir l'adresse email
git config --global user.email "prenom.nom@exemple.com"

# Définir l'éditeur par défaut

# Afficher la configuration actuelle
git config --list

# Afficher un paramètre spécifique

2.3 Commandes Fondamentales

2.3.1 Initialisation et Clonage

Listing 2.3 – Initialisation et clonage d'un dépôt

# Initialiser un nouveau dépôt local
git init

# Initialiser un dépôt avec un nom de répertoire
git init mon-projet

# Cloner un dépôt distant (HTTPS)
git clone https://github.com/utilisateur/depot.git

git clone git@github.com:utilisateur/depot.git

# Cloner sans l'historique complet (shallow clone)
git clone --depth 1 https://github.com/utilisateur/depot.git

2.3.2 Suivre les Fichiers (Staging)

Zone de transit (Staging Area) : Espace intermédiaire où les fichiers modifiés sont préparés avant d'être validés. Elle permet de grouper logiquement vos modifications (par exemple via git add).

Listing 2.4 – Zone de transit (staging area)

# Afficher l'état du dépôt
git status

# Afficher l'état en format court
git status -s

# Ajouter un fichier spécifique à la zone de transit
git add fichier.txt

# Ajouter tous les fichiers modifiés
git add .

# Ajouter tous les fichiers d'une extension
git add *.java

# Ajouter de manière interactive (sélectif)
git add -p

# Retirer un fichier de la zone de transit
git restore --staged fichier.txt

# Ancienne syntaxe équivalente
git reset HEAD fichier.txt

2.3.3 Valider les Modifications (Commit)

Commit : Validation permanente d'un ensemble de modifications avec un message descriptif. Chaque commit crée un point de sauvegarde immuable (un "snapshot") dans l'historique de votre projet.

Listing 2.5 – Commandes de commit

# Créer un commit avec un message
git commit -m "feat: ajout de la fonctionnalité de connexion"

# Ajouter et committer en une seule commande
git commit -am "fix: correction du bug d'authentification"

# Amender le dernier commit (message ou contenu)
git commit --amend -m "feat: nouveau message"

# Amender sans changer le message
git commit --amend --no-edit

# Commit vide (utile pour CI)
git commit --allow-empty -m "trigger CI"

2.3.4 Consulter l'Historique

Listing 2.6 – Consultation de l'historique

# Afficher l'historique des commits
git log

# Afficher l'historique en une ligne par commit
git log --oneline

# Afficher avec graphe des branches
git log --oneline --graph --all

# Afficher les n derniers commits
git log -n 5

# Filtrer par auteur
git log --author="AATTOURI"

# Filtrer par date
git log --since="2024-01-01" --until="2024-12-31"

# Afficher les modifications d'un commit
git show <hash-commit>

# Afficher les différences non committées
git diff

# Afficher les différences entre la zone de transit et le dernier commit
git diff --staged

2.3.5 Gestion des Branches

Branche (Branch) : Une ligne de développement indépendante. Elle permet de travailler sur de nouvelles fonctionnalités ou de corriger des bugs de manière isolée sans affecter la ligne principale du projet (généralement nommée main).

Listing 2.7 – Gestion des branches

# Lister les branches locales
git branch

# Lister toutes les branches (locales et distantes)
git branch -a

# Créer une nouvelle branche
git branch feature/ma-fonctionnalite

# Basculer sur une branche existante
git checkout develop
git switch develop          # nouvelle syntaxe recommandée

# Créer et basculer sur une nouvelle branche
git checkout -b feature/ma-fonctionnalite
git switch -c feature/ma-fonctionnalite   # nouvelle syntaxe

# Renommer une branche
git branch -m ancien-nom nouveau-nom

# Supprimer une branche locale
git branch -d feature/ma-fonctionnalite

# Forcer la suppression d'une branche non mergée
git branch -D feature/ma-fonctionnalite

# Supprimer une branche distante
git push origin --delete feature/ma-fonctionnalite

2.3.6 Fusion et Rebase

Fusion (Merge) : L'action d'intégrer l'historique et les modifications d'une branche dans une autre. Par exemple, après avoir terminé une tâche sur une branche de travail, vous la fusionnez dans la branche principale pour assembler le code.

Listing 2.8 – Fusion de branches

# Fusionner une branche dans la branche courante
git merge feature/ma-fonctionnalite

# Fusion sans fast-forward (conserve l'historique)
git merge --no-ff feature/ma-fonctionnalite

# Rebaser la branche courante sur main
git rebase main

# Rebaser interactivement les 3 derniers commits
git rebase -i HEAD~3

# Abandonner un rebase en cours
git rebase --abort

# Continuer après résolution de conflit
git rebase --continue

# Cherry-pick : appliquer un commit spécifique
git cherry-pick <hash-commit>

2.3.7 Interaction avec le Dépôt Distant

Dépôt Distant (Remote) : Une version de votre projet hébergée sur Internet ou un réseau (par exemple, sur GitHub, GitLab ou Bitbucket). Il sert de point de synchronisation central permettant à plusieurs développeurs de collaborer sur le même code.

Listing 2.9 – Commandes distantes (remote)

# Afficher les dépôts distants
git remote -v

# Ajouter un dépôt distant
git remote add origin https://github.com/utilisateur/depot.git

# Modifier l'URL d'un dépôt distant
git remote set-url origin git@github.com:utilisateur/depot.git

# Supprimer un dépôt distant
git remote remove origin

# Récupérer les modifications sans merger
git fetch origin

# Récupérer toutes les branches distantes
git fetch --all

# Tirer (fetch + merge) la branche courante
git pull

# Tirer avec rebase
git pull --rebase

# Pousser la branche courante vers le dépôt distant
git push origin main

# Pousser et configurer le suivi
git push -u origin feature/ma-fonctionnalite

# Pousser tous les tags
git push --tags

Listing 2.10 – Annulation et restauration

# Annuler les modifications d'un fichier (non staged)

2.3.9 Étiquettes (Tags)

Tag : Un marqueur immuable rattaché à un commit spécifique. Les tags sont généralement utilisés pour marquer les versions de publication d'un logiciel (par exemple, v1.0.0, v2.1.3).

Branche Rôle

develop Branche d'intégration principale
feature/* Nouvelles fonctionnalités

git flow release start 1.2.0

git flow hotfix start correction-critique

# Terminer un hotfix
git flow hotfix finish correction-critique

Dans cette approche, tous les développeurs committent directement sur une branche unique (main ou trunk). Les fonctionnalités non finies sont masquées par des feature flags.

Chapitre 3 : Intégration Continue (CI)

3.1 Définition et Principes

L'Intégration Continue (Continuous Integration ou CI) est une pratique de développement logicielle qui consiste à intégrer fréquemment les modifications de code au sein d'un dépôt partagé unique. Chaque intégration déclenche automatiquement une suite de builds et de tests afin de détecter et de corriger au plus tôt les régressions.

La mise en œuvre de la CI repose sur huit principes fondamentaux décrits dans le tableau suivant :

N° Principes fondamentaux de l'Intégration Continue
1Maintenir un dépôt de code unique et partagé.
2Automatiser la phase de construction (build).
3Rendre la construction auto-testable.
4Intégrer quotidiennement les modifications de code.
5Assurer un build rapide (durée inférieure à 10 minutes).
6Exécuter les tests dans un environnement identique à la production.
7Assurer la transparence en rendant les résultats accessibles à tous.
8Automatiser le processus de déploiement.

3.2 Jenkins

3.2.1 Présentation

Jenkins est un serveur d'automatisation open-source développé en Java, s'imposant comme le standard incontournable pour concevoir des pipelines CI/CD. Son immense écosystème de plugins lui permet de s'interfacer nativement avec des technologies clés telles que Git, Docker, Kubernetes ou encore Slack.

3.2.4 Jenkinsfile – Pipeline Déclaratif vs Scripted

Le Jenkinsfile est un fichier textuel positionné à la racine du dépôt de code. Il concrétise l'approche de Pipeline as Code en décrivant l'intégralité du processus de livraison. Jenkins propose deux syntaxes pour écrire ces pipelines :

1. Pipeline Déclaratif (Recommandé) : Introduit une structure stricte et lisible (blocs pipeline, stages, steps). Il limite la complexité pour garantir une maintenance facile et permet à Jenkins de valider la syntaxe avant l'exécution. C'est l'approche standard moderne.

2. Pipeline Scripted (Groovy) : L'approche historique, basée sur des scripts Groovy purs. Elle offre une flexibilité absolue (boucles complexes, logique impérative) mais au prix d'une lisibilité réduite et d'une maintenance plus complexe.

Note : L'exemple déclaratif ci-dessous est volontairement complet et détaillé (tests, SonarQube, Docker, Kubernetes, notifications) car il représente un standard industriel (Gold Standard) pour un pipeline de production du monde réel. Il couvre la grande majorité des cas d'usage professionnels.

Anatomie détaillée d'un Jenkinsfile Déclaratif

Pour bien comprendre le pipeline déclaratif, voici une explication bloc par bloc. Certains blocs sont obligatoires (la syntaxe même de Jenkins), tandis que le contenu des étapes (steps) est spécifique à votre projet.

1. Le conteneur principal et l'Agent (Syntaxe Obligatoire)

Le bloc pipeline doit toujours englober tout le fichier. L'instruction agent est requise car elle indique à Jenkins où exécuter le pipeline.

pipeline {
    // OBLIGATOIRE : 'agent any' exécute le pipeline sur n'importe quel nœud disponible.
    agent any
    
    /* SCÉNARIO PROJET : 
       Si votre projet nécessite un environnement précis sans polluer le serveur,
       vous pouvez forcer l'exécution dans un conteneur Docker spécifique :
       agent { docker { image 'node:18-alpine' } } 
    */
2. Configuration de l'environnement (Optionnel mais recommandé)

Ce bloc définit les variables globales et les options d'exécution du pipeline.

    environment {
        // OPTIONNEL : Variables d'environnement injectées dans tout le pipeline.
        APP_VERSION = '1.0.0'
        DOCKER_IMAGE = "monapp:${APP_VERSION}"
        
        /* SCÉNARIO PROJET :
           Pour un projet Java : MAVEN_HOME = tool 'Maven-3.9'
           Pour un projet JS   : NODE_ENV = 'production' 
        */
    }

    options {
        // OPTIONNEL : Bonnes pratiques pour la stabilité du serveur
        timeout(time: 30, unit: 'MINUTES') // Évite qu'un job bloqué tourne à l'infini
        disableConcurrentBuilds()          // Empêche deux builds de tourner en même temps
    }
3. Les Étapes / Stages (Syntaxe Obligatoire)

C'est le cœur du pipeline. La hiérarchie stages > stage > steps doit toujours être respectée. Cependant, les commandes exécutées (les sh) dépendent totalement de votre code.

    stages {
        stage('Checkout') {
            steps {
                // Étape quasi-universelle : récupérer le code source depuis Git
                git branch: 'main', url: 'https://github.com/utilisateur/depot.git'
            }
        }

        stage('Build & Tests') {
            steps {
                /* SCÉNARIO PROJET : C'est ici que le code diffère selon le langage !
                   - Projet Java/Maven : sh "mvn clean package"
                   - Projet Node.js    : sh "npm install && npm run test"
                   - Projet Python     : sh "pip install -r req.txt && pytest"
                   - Projet Go         : sh "go build && go test ./..."
                */
                sh "mvn clean package" // Exemple pour Java
            }
        }

        stage('Deploiement (Conditionnel)') {
            // OPTIONNEL : 'when' permet d'exécuter un stage uniquement sous certaines conditions
            when {
                branch 'main' // Ne s'exécute que sur la branche principale
            }
            steps {
                sh "kubectl apply -f k8s/production/"
            }
        }
    }
4. Actions Post-Exécution (Optionnel)

Le bloc post permet d'exécuter des actions à la fin du pipeline, en fonction du statut final de celui-ci (succès, échec, ou toujours).

    post {
        success {
            // Exécuté uniquement si tous les stages ont réussi
            slackSend channel: '#devops', message: "Build REUSSI !"
        }
        failure {
            // Exécuté en cas d'erreur dans le pipeline
            emailext to: 'equipe@exemple.com', subject: "ECHEC du build"
        }
        always {
            // OBLIGATOIRE EN PRATIQUE : Toujours nettoyer l'espace de travail
            // pour éviter que le disque du serveur Jenkins ne sature.
            cleanWs()
        }
    }
} // Fin du bloc obligatoire 'pipeline'

Anatomie d'un Pipeline Scripted (Groovy)

Contrairement au pipeline déclaratif, l'approche Scripted est beaucoup plus libre et ressemble à un script de programmation classique. Voici comment il se décompose :

1. Allocation du Nœud (Syntaxe Obligatoire)

Le bloc node est le point d'entrée. Il demande à Jenkins d'allouer une machine (un agent) et un espace de travail pour exécuter le code.

// OBLIGATOIRE : 'node' alloue un agent pour exécuter le script.
// On peut spécifier un label (ex: 'linux', 'windows') ou laisser vide node() pour n'importe quel agent.
node('linux') {
    
    // OPTIONNEL : Déclaration de variables globales en Groovy pur
    // SCÉNARIO PROJET : Récupération du chemin d'un outil (comme Maven) configuré dans Jenkins
    def mavenHome = tool 'Maven-3.9'
2. Étapes et Logique (Totalement Flexible)

Dans un script Groovy, les stages sont purement visuels dans l'interface Jenkins. Vous n'avez pas besoin de blocs steps, et vous gérez vous-même toute la logique impérative (boucles, try/catch, if/else).

    stage('Checkout') {
        // OBLIGATOIRE (pratique) : Récupérer le code source depuis le gestionnaire de versions
        checkout scm
    }

    stage('Build & Tests') {
        /* SCÉNARIO PROJET : Logique métier et gestion manuelle des erreurs
           Comme nous sommes en Groovy pur, il n'y a pas de bloc magique 'post { failure { ... } }'.
           Nous devons utiliser un bon vieux try/catch de programmation pour intercepter les plantages.
        */
        try {
            // Commande spécifique au projet (Ex: Maven pour Java)
            // Pour Node.js, ce serait : sh "npm install && npm test"
            sh "${mavenHome}/bin/mvn clean package" 
        } catch (Exception e) {
            // GESTION MANUELLE : On marque explicitement le build en échec
            currentBuild.result = 'FAILURE'
            error "Le build a echoue : ${e.message}"
        }
    }

    stage('Deploiement Conditionnel') {
        /* SCÉNARIO PROJET : Logique conditionnelle manuelle
           Contrairement au déclaratif qui utilise 'when { branch "main" }',
           ici nous utilisons une simple instruction 'if' native à Groovy.
        */
        if (env.BRANCH_NAME == 'main') {
            sh 'kubectl apply -f k8s/production/'
        }
    }
} // Fin de l'allocation du nœud (node)

3.2.5 Gestion des Credentials Jenkins

L'utilisation des différents types de secrets (credentials) gérés de manière sécurisée par Jenkins s'articule comme suit :

Type de Secret Description et Syntaxe Contextuelle
Username / PasswordInjecte séparément un nom d'utilisateur et un mot de passe sous forme de variables
Secret TextUtilisé généralement pour stocker un jeton d'API (API token) ou une clé de sécurité brute
Fichier SecretPermet de manipuler un fichier confidentiel (ex: configuration kubeconfig) via son chemin local temporaire
SSH Private KeyInjecte une clé privée SSH et un identifiant utilisateur associé pour s'authentifier à distance

Anatomie de l'Injection de Credentials

Dans Jenkins, on n'écrit jamais de mots de passe ou de clés en clair dans un code source. La bonne pratique impose d'utiliser la fonction withCredentials qui injecte temporairement et de manière masquée les secrets le temps d'un bloc d'exécution.

1. Type : Utilisateur & Mot de passe (Username/Password)

Idéal pour se connecter à un registre Docker, une base de données, ou une API standard.

// SYNTAXE OBLIGATOIRE : La fonction 'withCredentials' et le binding 'usernamePassword'
withCredentials([usernamePassword(
    credentialsId: 'docker-hub-id', // ID exact tel que configuré dans l'interface Jenkins
    usernameVariable: 'USER',       // Variable injectée contenant l'utilisateur
    passwordVariable: 'PASS'        // Variable injectée contenant le mot de passe
)]) {
    /* SCÉNARIO PROJET : Connexion automatisée à Docker Hub pour pousser une image.
       Jenkins remplacera automatiquement la valeur par des astérisques (***) dans les logs
       si elle devait être affichée par erreur.
    */
    sh "echo ${PASS} | docker login -u ${USER} --password-stdin"
}
2. Type : Texte Secret (Secret Text)

Utilisé pour des chaînes de caractères uniques, comme un jeton d'API (Token Slack, SonarQube, AWS Access Key).

// SYNTAXE OBLIGATOIRE : Le binding 'string'
withCredentials([string(
    credentialsId: 'api-token', 
    variable: 'TOKEN'
)]) {
    // SCÉNARIO PROJET : Authentification HTTP sécurisée via un Bearer Token
    sh "curl -H 'Authorization: Bearer ${TOKEN}' https://api.exemple.com/data"
}
3. Type : Fichier Secret (Secret File)

Permet d'injecter un fichier complet (ex: certificat .pem, configuration kubeconfig). Jenkins copie le fichier temporairement sur l'agent et s'assure de le supprimer à la fin du bloc.

// SYNTAXE OBLIGATOIRE : Le binding 'file'
withCredentials([file(
    credentialsId: 'k8s-config', 
    variable: 'KUBECONFIG_PATH' // La variable contiendra le chemin local du fichier temporaire
)]) {
    // SCÉNARIO PROJET : Authentification Kubernetes pour déclencher un déploiement
    sh "kubectl --kubeconfig=${KUBECONFIG_PATH} apply -f deployment.yaml"
}
4. Type : Clé Privée SSH (SSH Private Key)

Indispensable pour se connecter en SSH à un serveur de production ou pour cloner un dépôt Git privé.

// SYNTAXE OBLIGATOIRE : Le binding 'sshUserPrivateKey'
withCredentials([sshUserPrivateKey(
    credentialsId: 'prod-ssh-key',
    keyFileVariable: 'SSH_KEY',   // Chemin vers le fichier de la clé privée
    usernameVariable: 'SSH_USER'  // L'utilisateur associé (ex: ubuntu, root)
)]) {
    // SCÉNARIO PROJET : Exécuter un script d'installation sur une VM distante
    sh "ssh -i ${SSH_KEY} ${SSH_USER}@serveur.exemple.com '/opt/scripts/deploy.sh'"
}

3.2.6 GitHub Actions – Alternative à Jenkins

GitHub Actions est une alternative native à Jenkins intégrée à l'écosystème GitHub. Elle s'appuie sur une description declarative au format YAML pour automatiser les workflows de livraison logicielle.

Anatomie détaillée d'un Workflow GitHub Actions

Contrairement à Jenkins qui utilise Groovy, GitHub Actions utilise la syntaxe YAML. Ce fichier doit obligatoirement être placé dans le dossier .github/workflows/ de votre dépôt.

1. Déclencheurs (Triggers) - Syntaxe Obligatoire

Le bloc on: définit quand le pipeline doit s'exécuter.

# OBLIGATOIRE : Nom du workflow affiché dans l'interface GitHub
name: Pipeline CI/CD

# OBLIGATOIRE : Événements qui déclenchent le workflow
on:
  # SCÉNARIO PROJET : Déclenchement automatique lors d'un push sur 'main' ou 'develop'
  push:
    branches: [main, develop]
  # SCÉNARIO PROJET : Exécuter les tests avant d'accepter une fusion (Pull Request)
  pull_request:
    branches: [main]

# OPTIONNEL : Variables d'environnement partagées entre tous les jobs
env:
  DOCKER_IMAGE: monapp
2. Configuration du Job (Job Setup)

Les jobs s'exécutent par défaut en parallèle. Chaque job doit déclarer sur quelle machine (runner) il tourne via runs-on.

jobs:
  # OBLIGATOIRE : ID du premier job
  build-and-test:
    # OBLIGATOIRE : L'environnement d'exécution (runner)
    # L'alternative serait 'windows-latest' ou 'macos-latest' selon vos besoins
    runs-on: ubuntu-latest
    
    # OBLIGATOIRE : La liste séquentielle des étapes pour ce job
    steps:
      # Étape universelle : Récupérer le code source
      - name: Checkout du code
        uses: actions/checkout@v4
3. Les Actions (Uses) et Commandes (Run)

Dans GitHub Actions, on utilise massivement des Actions pré-fabriquées (mot-clé uses) pour éviter de réécrire des scripts complexes, ou bien des commandes natives avec run.

      # SCÉNARIO PROJET : Action pré-fabriquée pour configurer l'environnement Java
      # Pour Node.js, ce serait : uses: actions/setup-node@v4
      - name: Configuration de Java 17
        uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'

      # OPTIONNEL MAIS RECOMMANDÉ : Mettre en cache les dépendances pour accélérer les builds futurs
      - name: Cache Maven
        uses: actions/cache@v3
        with:
          path: ~/.m2
          key: ${{ runner.os }}-m2-${{ hashFiles('**/pom.xml') }}

      # SCÉNARIO PROJET : Commande d'exécution métier spécifique au projet
      - name: Build et tests
        run: mvn clean verify

      # OPTIONNEL : Archiver les rapports générés par les tests pour consultation
      - name: Publication des resultats de tests
        uses: actions/upload-artifact@v4
        with:
          name: test-results
          path: target/surefire-reports/
4. Dépendances entre Jobs et Authentification

On utilise needs pour forcer un job à attendre la fin d'un autre, et la syntaxe ${{ secrets... }} pour injecter des credentials stockés en toute sécurité dans l'interface GitHub.

  # Deuxième job (Docker)
  docker:
    # OBLIGATOIRE POUR LA SÉQUENCE : Attend que le job 'build-and-test' réussisse
    needs: build-and-test
    runs-on: ubuntu-latest
    
    # CONDITION DE DÉPLOIEMENT : S'exécute UNIQUEMENT sur la branche 'main'
    if: github.ref == 'refs/heads/main'
    
    steps:
      - uses: actions/checkout@v4

      # INJECTION DE SECRETS : Connexion au registre sans exposer les mots de passe
      - name: Login Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_PASSWORD }}

      # DÉPLOIEMENT : Création et envoi de l'image Docker finale
      - name: Build et Push de l'image
        uses: docker/build-push-action@v5
        with:
          push: true
          tags: ${{ secrets.DOCKER_USERNAME }}/${{ env.DOCKER_IMAGE }}:latest

Chapitre 4 — Livraison et Déploiement Continu (CD)

4.1 Définitions

Livraison Continue (Continuous Delivery) : extension de la CI qui garantit que le code peut être déployé en production à tout moment, après validation manuelle.
Déploiement Continu (Continuous Deployment) : extension de la livraison continue où chaque modification validée par les tests est automatiquement déployée en production, sans intervention humaine.

4.2 Stratégies de Déploiement

4.2.1 Blue-Green Deployment

Deux environnements de production totalement identiques et isolés coexistent : l'environnement Blue (qui héberge la version actuelle en direct) et l'environnement Green (qui héberge la nouvelle version).

  • Fonctionnement : La nouvelle version est déployée et testée en toute sécurité sur "Green". Une fois validée, le routeur redirige instantanément 100% du trafic de Blue vers Green.
  • Avantage principal : Zéro temps d'arrêt (Zero Downtime) et retour en arrière (Rollback) instantané en cas de problème (il suffit de rediriger le trafic vers Blue).
  • Cas d'usage idéal : Applications critiques nécessitant une disponibilité totale et où l'infrastructure permet de doubler temporairement les ressources.

4.2.2 Canary Deployment (Déploiement Canari)

Inspirée des canaris utilisés dans les mines de charbon pour détecter les gaz toxiques, cette stratégie consiste à déployer la nouvelle version auprès d'un très petit sous-ensemble d'utilisateurs avant de la généraliser.

  • Fonctionnement : La nouvelle version est déployée pour, par exemple, 5 % du trafic. Les équipes surveillent les métriques (erreurs, latence). Si tout est stable, la version est déployée à 25 %, puis 100 %.
  • Avantage principal : Minimise massivement le rayon d'impact d'un bug critique en production. Seuls quelques utilisateurs seront affectés.
  • Cas d'usage idéal : Lancement de nouvelles fonctionnalités majeures avec un fort risque de régression technique ou d'expérience utilisateur.

4.2.3 Rolling Update (Mise à jour progressive)

Plutôt que de remplacer toute l'application d'un coup ou d'avoir deux environnements complets, on met à jour les instances du serveur une par une (ou par petits groupes de noeuds).

  • Fonctionnement : Si on a 10 serveurs, le répartiteur de charge retire le Serveur 1, le met à jour avec la nouvelle version, le remet en ligne, puis passe au Serveur 2, etc., sans interruption de service globale.
  • Avantage principal : Ne nécessite pas le double d'infrastructure (contrairement au Blue-Green) tout en assurant une haute disponibilité.
  • Cas d'usage idéal : Applications standard hébergées sur Kubernetes ou dans des groupes d'auto-scaling Cloud (AWS ASG), où les mises à jour progressives sont gérées nativement.

4.2.4 Feature Flags (Drapeaux de Fonctionnalités)

Cette approche découple complètement le déploiement du code de la "libération" (release) de la fonctionnalité. Le code est poussé en production, mais la fonctionnalité est masquée par des indicateurs configurables (variables).

  • Fonctionnement : Une simple condition if (featureEnabled("nouveau_panier")) englobe le nouveau code. La variable peut être activée depuis une interface d'administration pour certains utilisateurs cibles, sans redéployer.
  • Avantage principal : Permet de tester en production avec de vrais utilisateurs, de faire de l'A/B testing, et de désactiver instantanément une fonctionnalité défectueuse sans toucher au pipeline CI/CD.
  • Cas d'usage idéal : Développement en mode "Trunk-Based" et tests de nouvelles interfaces (A/B testing) ou fonctionnalités non terminées en production.

5.5 Le Dockerfile

Anatomie détaillée d'un Dockerfile

Un Dockerfile est un script de construction contenant des instructions successives. Chaque instruction crée une nouvelle "couche" (layer) dans l'image finale. L'ordre est critique pour optimiser le cache de construction.

1. La Base et les Métadonnées (Syntaxe Obligatoire)

Tout Dockerfile doit obligatoirement commencer par l'instruction FROM qui définit le système de départ (généralement une image officielle allégée).

# OBLIGATOIRE : Définit l'image de base (ici Python 3.11 allégé)
FROM python:3.11-slim AS base

# OPTIONNEL : Ajoute des métadonnées informatives
LABEL maintainer="aattouri@exemple.com"
LABEL version="1.0"
2. Configuration de l'Environnement

On définit le dossier de travail et les variables nécessaires pour le système.

# OBLIGATOIRE EN PRATIQUE : Définit le répertoire où les commandes s'exécuteront
WORKDIR /app

# OPTIONNEL : Arguments utilisables UNIQUEMENT pendant le 'docker build'
ARG APP_VERSION=1.0.0

# OBLIGATOIRE SELON PROJET : Variables d'environnement persistantes (au runtime)
ENV APP_VERSION=${APP_VERSION}
ENV PYTHONUNBUFFERED=1
3. Installation des Dépendances (Optimisation du Cache)

Pour ne pas tout réinstaller à chaque changement de code, on copie d'abord les fichiers de dépendances, on installe, puis on copie le reste.

# OBLIGATOIRE : Installer les paquets système Linux nécessaires
RUN apt-get update && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*

# OPTIMISATION CACHE : On copie uniquement les dépendances en premier
COPY requirements.txt .

# RUN : On exécute l'installation des dépendances Python
RUN pip install --no-cache-dir -r requirements.txt
4. Code Source et Sécurité

On importe le code applicatif et on bascule sur un utilisateur restreint.

# OBLIGATOIRE : Copier le code source de l'application
COPY src/ ./src/

# BONNE PRATIQUE DE SÉCURITÉ : Ne jamais exécuter l'application en tant que 'root'
RUN adduser --system --group appuser
USER appuser
5. Exécution et Exposition

Instructions finales qui contrôlent le comportement du conteneur lors de son démarrage effectif.

# OPTIONNEL (Documentatif) : Indique le port sur lequel l'application écoute
EXPOSE 8080

# OPTIONNEL : Déclare un dossier destiné à être monté en volume externe
VOLUME ["/app/logs"]

# BONNE PRATIQUE : Permet au routeur de savoir si l'application a planté
HEALTHCHECK --interval=30s --timeout=5s CMD curl -f http://localhost:8080/health || exit 1

# OBLIGATOIRE : L'exécutable principal du conteneur
ENTRYPOINT ["python", "-m", "gunicorn"]

# OPTIONNEL : Les arguments par défaut passés à ENTRYPOINT
CMD ["--bind", "0.0.0.0:8080", "app:application"]

Listing 5.5 – Multi-stage Build (bonne pratique)

# Stage 1 : Build
FROM maven:3.9-openjdk-17 AS builder
WORKDIR /build
COPY pom.xml .
COPY src ./src
RUN mvn clean package -DskipTests

# Stage 2 : Production (image finale légère)
FROM openjdk:17-jre-slim AS production
WORKDIR /app

# Créer un utilisateur non-root

    && adduser --system --uid 1001 --gid 1001 appuser

USER appuser
EXPOSE 8080

HEALTHCHECK --interval=30s --timeout=5s \
    CMD wget -qO- http://localhost:8080/actuator/health || exit 1

ENTRYPOINT ["java", "-jar", "/app/app.jar"]

5.8 Docker Compose

Docker Compose permet de définir et de gérer des applications multi-conteneurs via un fichier de configuration déclaratif.

Anatomie détaillée d'un fichier docker-compose.yml

Le fichier Compose est un manifeste YAML qui orchestre plusieurs conteneurs pour qu'ils fonctionnent ensemble (Base de données, Cache, Serveur Web, Application). Il se divise en 3 sections principales : networks, volumes, et services.

1. Topologie (Réseaux et Volumes Globaux)

Avant de définir les conteneurs, on déclare les réseaux virtuels pour les faire communiquer de manière isolée, et les volumes pour stocker leurs données de façon permanente.

version: '3.9' # Indique la version de la syntaxe YAML (optionnel dans les versions récentes)

networks:
  frontend:
    driver: bridge # Réseau "public" (accessible depuis l'hôte)
  backend:
    driver: bridge
    internal: true # Réseau "privé" (totalement isolé de l'hôte, idéal pour sécuriser une BDD)

volumes:
  db-data:     # Déclare un volume global pour la base de données
  redis-data:  # Déclare un volume pour le cache
  app-logs:    # Déclare un volume pour les journaux d'application
2. Services d'Infrastructure (Base de données & Cache)

On définit les composants back-end. On utilise des images officielles pré-construites (postgres, redis) et on y connecte les volumes globaux créés précédemment.

services:
  db: # Nom du service (sera utilisé comme nom d'hôte sur le réseau interne)
    image: postgres:15-alpine
    container_name: postgres
    restart: unless-stopped # Redémarre automatiquement sauf si on l'arrête manuellement
    environment:
      POSTGRES_DB: mabase
      POSTGRES_USER: ${DB_USER:-admin} # Utilise une variable d'environnement, ou 'admin' par défaut
      POSTGRES_PASSWORD: ${DB_PASSWORD:?DB_PASSWORD requis} # Échoue si la variable n'existe pas
    volumes:
      - db-data:/var/lib/postgresql/data # Montage du volume global 'db-data'
      - ./init.sql:/docker-entrypoint-initdb.d/init.sql:ro # Bind Mount local en lecture seule (ro)
    networks:
      - backend # Connecté UNIQUEMENT au réseau privé
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER}"]
      interval: 10s # Vérifie toutes les 10s si la BDD est prête à accepter des connexions

  redis:
    image: redis:7-alpine
    restart: unless-stopped
    command: redis-server --requirepass ${REDIS_PASSWORD} # Surcharge la commande de l'image
    volumes:
      - redis-data:/data
    networks:
      - backend
3. Le Service Applicatif (Code Métier)

Contrairement à la BDD qui télécharge une image existante, l'application métier est construite à la volée (build) à partir du code source local.

  app:
    build:
      context: . # Cherche le 'Dockerfile' dans le dossier courant
      args:
        APP_VERSION: ${APP_VERSION:-1.0.0}
    image: monapp:${APP_VERSION:-latest} # Nomme l'image une fois qu'elle est construite
    restart: unless-stopped
    environment:
      # L'application communique avec la BDD en utilisant le nom du service 'db' !
      DATABASE_URL: postgresql://admin:${DB_PASSWORD}@db:5432/mabase
      REDIS_URL: redis://:${REDIS_PASSWORD}@redis:6379
    ports:
      - "8080:8080" # Mappe le port 8080 du conteneur sur le port 8080 de l'hôte
    depends_on:
      db:
        condition: service_healthy # Attend intelligemment que la BDD soit PRÊTE (pas juste démarrée)
      redis:
        condition: service_healthy
    networks:
      - frontend # Connecté aux DEUX réseaux pour faire le pont entre Nginx et la BDD
      - backend
    deploy:
      resources:
        limits: # Empêche l'application de consommer toute la RAM du serveur
          cpus: '1'
          memory: 512M
4. Le Proxy Inverse (Point d'entrée public)

C'est la seule brique véritablement exposée au monde extérieur. Elle reçoit les requêtes HTTP/HTTPS et les redirige vers l'application.

  nginx:
    image: nginx:alpine
    container_name: nginx
    restart: unless-stopped
    ports:
      - "80:80"   # HTTP
      - "443:443" # HTTPS
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro # Importe la configuration Nginx locale
      - ./nginx/ssl:/etc/nginx/ssl:ro               # Importe les certificats SSL locaux
    depends_on:
      - app # S'assure que l'application démarre avant le proxy
    networks:
      - frontend # Connecté UNIQUEMENT au réseau public

6.4.2 Pod

Anatomie détaillée d'un Manifeste de Pod

Un Pod est la plus petite unité déployable dans Kubernetes. Ce fichier YAML décrit la configuration exacte du ou des conteneurs à lancer, les ressources qui leur sont allouées, et les méthodes pour vérifier leur bon fonctionnement.

1. En-tête et Métadonnées

On définit le type d'objet Kubernetes que l'on veut créer, ainsi que ses informations d'identification (nom, espace de travail, étiquettes de regroupement).

apiVersion: v1 # Version de l'API Kubernetes utilisée
kind: Pod      # Le type de ressource à créer
metadata:
  name: mon-pod          # Nom unique du Pod
  namespace: default     # Isolation logique (espace de travail)
  labels:                # Paires clé-valeur pour identifier/filtrer ce Pod plus tard
    app: monapp
    version: "1.0"
2. Définition du Conteneur et de l'Environnement

La section spec décrit l'état désiré du Pod. On y définit l'image Docker à utiliser, les ports ouverts, et les variables d'environnement injectées.

spec:
  containers:
  - name: monapp           # Nom du conteneur dans le Pod
    image: monapp:1.0.0    # Image Docker à télécharger
    ports:
    - containerPort: 8080  # Port interne sur lequel l'application écoute
    env:
    - name: APP_ENV
      value: "production"  # Variable d'environnement en clair
    - name: DB_PASSWORD
      valueFrom:
        secretKeyRef:      # Récupère le mot de passe depuis un objet "Secret" sécurisé
          name: db-secret
          key: password
3. Gestion des Ressources (CPU & RAM)

Crucial pour la stabilité du cluster. On définit le minimum garanti pour que le Pod démarre (requests) et le maximum autorisé pour éviter qu'il ne sature le nœud (limits).

    resources:
      requests:          # Ce qui est GARANTI (utilisé par le scheduler pour placer le Pod)
        memory: "128Mi"  # 128 Mégaoctets
        cpu: "250m"      # 250 millicores (1/4 de processeur)
      limits:            # Le plafond MAX (le conteneur sera tué s'il dépasse la RAM)
        memory: "512Mi"
        cpu: "1000m"     # 1 cœur complet
4. Sondes de Santé (Probes)

Kubernetes vérifie automatiquement si l'application fonctionne bien grâce à ces requêtes réseau régulières.

    livenessProbe:       # Vérifie si l'app est "vivante" (la tue et la redémarre si elle plante)
      httpGet:
        path: /health
        port: 8080
      initialDelaySeconds: 30 # Attend 30s après le démarrage avant de commencer à tester
      periodSeconds: 10       # Refait le test toutes les 10s
    
    readinessProbe:      # Vérifie si l'app est "prête" à recevoir du trafic utilisateur
      httpGet:
        path: /ready
        port: 8080
      initialDelaySeconds: 5
      periodSeconds: 5
      
  restartPolicy: Always  # Politique de redémarrage (Toujours redémarrer en cas d'arrêt)

6.4.3 Deployment

Anatomie détaillée d'un Manifeste de Deployment

Un Deployment est un contrôleur de haut niveau qui gère un ensemble de Pods identiques. Il s'assure qu'un nombre précis de réplicas tourne en permanence, et orchestre les mises à jour sans aucune coupure de service (Zéro-Downtime).

1. En-tête du Contrôleur

Définit l'identité du Deployment lui-même au sein du cluster.

apiVersion: apps/v1 # Utilise l'API 'apps' plutôt que la v1 classique
kind: Deployment
metadata:
  name: monapp           # Le nom du Deployment
  namespace: production  # Déployé dans l'espace 'production'
  labels:
    app: monapp
2. Stratégie de Scale et Rolling Update

C'est ici que la magie de Kubernetes opère. On définit COMBIEN de Pods on veut, QUELS Pods sont sous notre contrôle, et COMMENT appliquer la nouvelle version (ici, un par un).

spec:
  replicas: 3 # OBLIGATOIRE : On exige que 3 instances du Pod tournent en permanence
  selector:
    matchLabels:
      app: monapp # Le contrôleur "adopte" tous les Pods qui ont cette étiquette
  strategy:
    type: RollingUpdate # Mise à jour progressive au lieu de tout éteindre d'un coup
    rollingUpdate:
      maxSurge: 1       # Autorise la création de 1 Pod supplémentaire (4 max) pendant la maj
      maxUnavailable: 0 # Interdit d'avoir moins de 3 Pods en bonne santé pendant la maj
3. Le Moule du Pod (Template)

Le Deployment va utiliser ce modèle pour générer ses 3 réplicas. C'est exactement la même syntaxe qu'un fichier Pod classique, imbriquée ici.

  template:
    metadata:
      labels:
        app: monapp    # CRITIQUE : Cette étiquette doit correspondre au 'selector' ci-dessus !
        version: "2.0"
    spec:
      containers:
      - name: monapp
        image: monapp:2.0.0
        ports:
        - containerPort: 8080
4. Haute Disponibilité via l'Anti-Affinité

Une configuration avancée demandant à l'orchestrateur de disperser physiquement les Pods sur différents serveurs (Nœuds) pour survivre à une panne matérielle locale.

      affinity:
        podAntiAffinity: # Règles pour éloigner les Pods les uns des autres
          preferredDuringSchedulingIgnoredDuringExecution: # Une "préférence" (pas une obligation stricte)
          - weight: 100
            podAffinityTerm:
              labelSelector:
                matchExpressions:
                - key: app
                  operator: In
                  values:
                  - monapp
              # Demande au scheduler de ne pas placer deux Pods 'monapp' sur le même serveur (hostname)
              topologyKey: kubernetes.io/hostname
5. Robustesse et Arrêt Gracieux

On s'assure que le Pod a les ressources nécessaires et qu'il ne coupe pas brutalement les requêtes clients lorsqu'il est détruit (lors d'un scaling down par exemple).

        resources:
          requests:
            memory: "256Mi"
            cpu: "500m"
          limits:
            memory: "1Gi"
            cpu: "2000m"
        livenessProbe:
          httpGet:
            path: /actuator/health/liveness
            port: 8080
          initialDelaySeconds: 60
        readinessProbe:
          httpGet:
            path: /actuator/health/readiness
            port: 8080
      # Laisse 30 secondes au processus pour s'arrêter proprement au lieu d'un SIGKILL immédiat
      terminationGracePeriodSeconds: 30

6.4.6 PersistentVolume et PersistentVolumeClaim

Persistance des données : Dans Kubernetes, les Pods sont par nature éphémères (ils peuvent être détruits et recréés sur d'autres nœuds). Pour conserver des données de manière permanente (comme une base de données), K8s sépare l'infrastructure de la demande via deux ressources :

• PersistentVolume (PV) : L'espace de stockage physique réel (disque dur local, volume AWS EBS, NFS) provisionné par l'administrateur du cluster.
• PersistentVolumeClaim (PVC) : Une "demande" de stockage faite par l'application (ex: "J'ai besoin de 5Go en lecture/écriture"). Kubernetes trouve automatiquement un PV correspondant et le "lie" au PVC pour que le Pod puisse l'utiliser.

Listing 6.11 – PersistentVolume et PersistentVolumeClaim

# PersistentVolume (PV)
apiVersion: v1
kind: PersistentVolume
metadata:
  name: mon-pv
spec:
  capacity:
    storage: 10Gi
  volumeMode: Filesystem
  accessModes:
  - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: standard
  hostPath:
    path: /mnt/data

---
# PersistentVolumeClaim (PVC)
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mon-pvc
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
  storageClassName: standard

6.4.7 Ingress

Ingress : Un Ingress est le point d'entrée public de votre cluster Kubernetes. Contrairement à un simple service LoadBalancer qui nécessite une IP publique par application, l'Ingress agit comme un routeur intelligent (souvent basé sur Nginx). Il permet d'héberger plusieurs noms de domaine sur une seule IP, de configurer le routage basé sur l'URL (ex: /api vers le backend, / vers le frontend), et de gérer centralement les certificats de sécurité SSL/HTTPS.

Listing 6.13 – Manifeste Ingress

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: mon-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - app.exemple.com
    secretName: mon-tls
  rules:
  - host: app.exemple.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-service
            port:
              number: 80
      - path: /
        pathType: Prefix
        backend:
          service:
            name: frontend-service
            port:
              number: 80

Chapitre 7 — Infrastructure as Code

7.1 Introduction

Infrastructure as Code (IaC) : pratique consistant à décrire et à gérer l'infrastructure informatique (serveurs, réseaux, bases de données, etc.) sous forme de fichiers de configuration versionnables et automatisables, plutôt que par des interventions manuelles.

Avantages de l'IaC :

  • Reproductibilité et cohérence entre les environnements.
  • Versionnage et traçabilité des modifications.
  • Automatisation et rapidité de provisionnement.
  • Réduction des erreurs humaines.
  • Documentation vivante de l'infrastructure.

    • 7.2 Terraform

    7.2.4 Exemple de Configuration Terraform

    Anatomie détaillée d'une Configuration Terraform

    Ce fichier main.tf déclare l'infrastructure souhaitée sur AWS. Terraform se chargera de calculer le différentiel et d'appliquer les changements via les API Cloud.

    1. Configuration Terraform & Provider

    On définit la version de Terraform requise, les fournisseurs cloud utilisés, et l'endroit où stocker l'état (le fichier tfstate).

    terraform {
  required_version = ">= 1.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
  backend "s3" {           # Le "backend" définit où est stocké l'état (tfstate)
    bucket = "mon-tfstate" # Utilisation d'un bucket AWS S3 pour le stockage distant partagé
    key    = "production/terraform.tfstate"
    region = "eu-west-1"
  }
}

provider "aws" {
  region = var.region
  default_tags {           # Tags par défaut appliqués automatiquement à TOUTES les ressources
    tags = {
      Environment = var.environment
      ManagedBy   = "Terraform"
    }
  }
}
    2. Déclaration des Variables

    Les variables permettent de rendre le code réutilisable pour différents environnements (dev, staging, prod).

    variable "region" {
  type    = string         # Type de la variable (chaîne de caractères)
  default = "eu-west-1"    # Valeur par défaut si non spécifiée par l'utilisateur
}

variable "environment" {
  type = string            # Pas de 'default' : l'utilisateur DOIT fournir cette valeur !
}

variable "instance_count" {
  type    = number
  default = 2              # Par défaut, on déploiera 2 serveurs
}
    3. Définition des Ressources

    Le cœur du code : les composants d'infrastructure réels à créer (Réseau, Serveurs, etc.).

    resource "aws_vpc" "principal" { # Type de ressource (VPC AWS) et nom local ("principal")
  cidr_block           = "10.0.0.0/16"
  enable_dns_hostnames = true
  tags = { Name = "vpc-${var.environment}" } # Interpolation : injecte la variable environment
}

resource "aws_instance" "serveur" {
  count         = var.instance_count      # Boucle "count" : créera autant de serveurs que spécifié
  ami           = data.aws_ami.ubuntu.id  # Récupère l'ID de l'image dynamique via un bloc "data"
  instance_type = "t3.micro"              # Taille du serveur (CPU/RAM)
  subnet_id     = aws_subnet.public.id
  tags = { Name = "serveur-${var.environment}-${count.index}" } # count.index ajoute 0, 1, 2...
}
    4. Sorties (Outputs)

    Les informations utiles retournées par Terraform une fois l'infrastructure déployée.

    output "instance_ips" {
  value = aws_instance.serveur[*].public_ip # Le [*] boucle et récupère la liste des IPs de TOUS les serveurs
}
